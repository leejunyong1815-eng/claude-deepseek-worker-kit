# 작은 기능 하나 구현해 보기

설치 후 오케스트레이터에게 기능을 요청하고, 로컬 워커의 구현과 외부 검증까지 이어지는 흐름을 확인한다.
사용자는 워커 이름이나 관리 명령을 직접 입력하지 않아도 된다. 이 안내를 따라 실행하면 Claude와 로컬 모델 요청이 발생한다.
현재 관리 모드는 Linux/WSL2와 로컬 파일시스템에서 사용한다.

## 1. 예제 프로젝트 시작

기존 프로젝트와 섞이지 않게 새 디렉터리를 만든다. 키트 설치와 로컬 모델 설정은 끝난 상태여야 한다.
예제 테스트는 Python 표준 라이브러리를 사용한다.

```bash
KIT_TEST_DIR=$(mktemp -d "${TMPDIR:-/tmp}/claude-kit-example.XXXXXX")
cd "$KIT_TEST_DIR"
git init
project-init .
claude-main
```

폴더 신뢰와 Claude 로그인 안내가 나오면 진행한다. `project-init`이 추가한 `KICKOFF_PROMPT.md`와 역할 파일을
오케스트레이터가 읽게 하면 작업 분해·워커 호출·검토를 맡길 수 있다. 실행기가 이 규칙을 자동 주입하는 것은 아니다.

## 2. 기능 요청

오케스트레이터에게 다음 요청을 전달한다.

```text
KICKOFF_PROMPT.md를 읽고 운영 규칙을 따라 줘.

text_utils.py에 normalize_spaces(text: str) -> str 함수를 구현해 줘.
앞뒤 공백을 없애고, 연속된 공백·탭·줄바꿈을 공백 하나로 합쳐 줘.
빈 문자열과 공백뿐인 문자열은 빈 문자열을 반환해야 해.
예: "  hello\tworld\n " → "hello world".

Python 표준 라이브러리 unittest로 테스트를 작성하고 로컬 워커에게 구현을 맡겨 줘.
이 새 예제 저장소에서는 운영 규칙·수용 테스트·태스크 입력을 포함하는 초기 기준 커밋 작성을 허용해.
기준 커밋에는 필요한 파일만 명시해서 넣고, 실제 구현은 별도 관리 worktree에서 수행해 줘.
외부 검증과 diff 검토까지 진행한 뒤 결과를 알려 줘. 완성 코드의 merge·commit·push는 하지 마.
```

초기 기준 커밋 허용은 **이 새 예제 저장소**에 대한 지시다. 기존 프로젝트의 미커밋 변경을 자동으로 커밋해도 된다는 뜻은 아니다.
Git 작성자 이름·이메일이 설정되어 있지 않거나 실행 권한이 부족하면 오케스트레이터가 필요한 설정을 안내한다.
사용자가 승인한 범위에서 설정한 뒤 진행한다.

## 3. 오케스트레이터가 진행할 일

1. 함수 계약과 독립 수용 테스트를 준비한다. 스켈레톤은 선택이며 구현 본문은 워커에게 맡긴다.
2. 허용된 초기 기준 커밋을 준비하고 태스크를 등록한다. 구현 프로필이 없으면 기본 프로필을 사용한다.
3. 별도 worktree에서 로컬 워커를 실행한다. 워커는 새 모듈 또는 주어진 함수 본문을 구현하고 지정된 테스트를 실행한다.
4. 실행기가 변경 경로와 실제 테스트 종료 코드를 검사한다. 검증 명령은 `python3 -B -m unittest discover -s tests -v`처럼 캐시를 만들지 않게 한다.
5. 오케스트레이터가 외부 검증 기록과 diff를 읽고 결과를 보고한다.

이 과정의 판단과 호출은 Claude가 운영 규칙에 따라 수행한다. 별도의 자동 작업 분배 서비스가 있는 것은 아니다.
권한·모델·검증 오류가 발생하면 성공으로 처리하지 않고 실패 이유와 해당 시도를 남긴다.

## 4. 결과 확인

보고에는 다음이 포함되어야 한다.

- task ID와 attempt ID, 기준 커밋, 작업 worktree 경로
- 워커 종료 코드와 외부 검증 종료 코드, timeout 여부
- 변경 파일 목록과 diff·로그 경로
- 정상 입력·빈 문자열·공백뿐인 입력·탭·줄바꿈 테스트 결과

검증 성공 상태와 유효한 코드 해시를 확인하고, 구현이 `text_utils.py`의 허용 범위에만 있는지 검토한다.
완성 코드는 보고된 worktree에 남아 있다. 원래 예제 디렉터리에는 초기 기준 커밋의 입력만 남는다. 새 모듈은 원본에 없거나 스켈레톤 상태여도 정상이다.
반영하려면 결과를 검토한 뒤 오케스트레이터에게 반영 범위를 별도로 요청한다.

“로컬 워커가 실제로 수행했는지와 막힌 부분을 알려 줘”처럼 진행 상황도 오케스트레이터에게 물을 수 있다.
서로 독립적인 구현 작업이 여러 개라면 각각 다른 worktree의 여러 워커로 분배할 수 있다.

예제 저장소·태스크 worktree·결과는 자동 삭제하지 않는다. 오케스트레이터 세션은 `/exit`로 끝낸다.
이 안내의 실제 모델 연동은 자동 테스트에 포함하지 않았으며, 키트의 회귀 검사는 모의 Claude로 수행한다.

직접 상태를 조사하거나 실행을 취소할 때는 [관리 CLI 사용법](MANAGED_TASKS.md),
대화형 워커 연결을 점검할 때는 [대화형 메시징 운영](INTERACTIVE.md)을 참고한다.
